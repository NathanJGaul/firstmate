# Telegram Remote Control

Telegram is an optional outbound transport for one active Firstmate home.
Firstmate polls Telegram with the Bot API `getUpdates` long-poll endpoint using a bounded 30-second timeout (maximum 50 seconds) and never opens an inbound webhook listener.

## Setup

Create a bot with BotFather, then run this from the Firstmate repository:

```sh
bin/fm-telegram.py setup
```

Setup prompts for the bot token without echoing it.
To supply it non-interactively, pipe it on standard input, for example `bin/fm-telegram.py setup < token-file`; the token is never accepted as a command-line argument, so it does not appear in process listings or shell history.
Setup validates the token with `getMe`, stores it in `config/telegram-bot-token` with mode `0600`, and prints a one-time pairing link plus a QR representation generated by the bundled Python renderer.
The QR is drawn with fixed black-on-white 256-color ANSI half blocks, quiet zone included, so it scans on light or dark terminal themes and fits a default 80x24 terminal; display it in a terminal that renders ANSI colors.
No administrator privileges, shell utility, or package installation is required.

Scan the QR code or open the link in Telegram.
The link opens the bot with `/start <nonce>`.
The nonce expires after ten minutes, works once, and rotates after pairing.
Pairing binds both Telegram user ID and chat ID.

## Enable polling

```sh
bin/fm-telegram.py enable
```

On Linux and macOS, enablement registers one `telegram-bot` process-event source for the active home; the existing process-event runner owns background execution, durable capture, wake publication, and restart recovery. On Windows, enablement starts the bundled Python polling worker and stores its private worker record without requiring a shell or service installation. Recorded remote workers are explicitly unsupported by the Windows owner boundary; status and steering return an error directing the operator to run Telegram on the remote Firstmate home.
Disable it with:

```sh
bin/fm-telegram.py disable
```

## Commands

- `/status [page]` reads one bounded durable fleet-status page.
- `/decisions [page]` reads one bounded open-decision page. Responses include a continuation command when another page exists.

Pages start at 1. The default page size is 10 and `FM_TELEGRAM_PAGE_SIZE` may set it from 1 through 50 for the polling process. When response compaction emits fewer rows than the configured page size, `pagination.next_command` carries a `page:offset` continuation so no rows are skipped.
- `/note <text>` queues a note through `bin/fm-inbox.sh`.
- `/steer <worker> <text>` sends reversible worker text through `bin/fm-send.sh`.

Unknown commands, unpaired users, mismatched chats, control bytes, oversized text, and unsafe worker IDs are rejected.
Telegram-only control cannot merge, delete, perform destructive or irreversible actions, handle credentials, or approve security-sensitive work.
Telegram text is never evaluated by a shell.

## Records and limits

Inbound updates, the durable Telegram inbox, processed-update markers, outbound responses, poll errors, and the next update offset live under `state/telegram/`. The inbox is written before deduplication, owner dispatch, and offset publication; unfinished effects resume from their recorded state.
The pairing record stores only a hash of the active nonce; the raw nonce appears only in the printed deep link.
Bot tokens never enter those records.
- A single Telegram response is limited to 256 KiB, command text to 4096 UTF-8 bytes, and outbound message text to 4096 characters. Status and decision pages stay within the Telegram message limit and expose `pagination.next_command` when more rows remain.
- Owner-script calls are limited to 20 seconds, and one `getUpdates` request waits up to 50 seconds.
- A `/steer` owner call is limited to twice `FM_SEND_REMOTE_BUDGET` plus 20 seconds (80 seconds by default), so a remote secondmate steer reaches `fm-send.sh`'s own unconfirmed-delivery outcome. When `fm-send.sh` reports a steer as unconfirmed (exit 3), or the call exceeds that bound, the reply says `steer unconfirmed - may have landed; check before resending` instead of reporting a rejection, the update is recorded with outcome `unconfirmed`, and the poll summary counts it under `unconfirmed` rather than `rejected`.
Repeated Telegram update IDs do not execute commands twice.

Polling errors are recorded as bounded local evidence and do not mutate pairing state.
A temporary Telegram outage leaves the update offset unchanged. A later process-event retry reuses the durable effect and outbound record, so a response may be delivered again but the local command is not re-executed.
A response that the Bot API permanently rejects with HTTP 400 or 403, such as one to a user who blocked the bot, is recorded as a terminal `rejected` delivery and the offset advances.
An offset older than Telegram's 24-hour update retention is not reused.
When polling uses a different bot than the one recorded in `state/telegram/bot-id`, it first moves the offset, inbox, inbound, processed-update, and outbound records into `state/telegram/retired/`.
